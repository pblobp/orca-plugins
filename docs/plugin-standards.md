# Plugin standards

Every plugin in this repository follows these rules. A plugin with a worker runs as the user, with
their files and credentials, and Orca updates it without asking. The rules exist to keep that safe.

## What the checks can and cannot do

CI rejects the patterns below. It cannot prove they are absent. A determined author can hide a
network call or generated code from any static check, for example behind a variable whose value
only exists at run time. The checks catch mistakes and the obvious. **The maintainer's review is the
control.** Every diff is read before it merges, and changes to `.github/`, `scripts/` and `policy/`
are read line by line, because a pull request runs its own copy of the checks and can weaken them.

`scripts/check-policy.mjs` has its own tests, including a corpus of known evasions it must reject
(`tests/scripts/corpus/evasion/`) and clean code it must accept (`tests/scripts/corpus/clean/`).
When someone finds a new way around a rule, the fix comes with a new file in that corpus.

## The rules

### Access

| Rule                                                                           | Why                                                                                      | How CI checks it                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Ask only for the capabilities the plugin uses, and explain each in its README  | Users approve access once; later updates that ask for nothing new install without asking | A change to `execution`, `main`, `capabilities`, or to the `commands`, `hooks`, `events`, `keybindings`, `panels` or `customEditors` contributions fails unless the plugin's `CHANGELOG.md` gains a line under an "Access" heading in the same pull request. A new plugin needs one too                                                                            |
| No network access, unless the README names the hosts and the policy lists them | A system plugin has no reason to talk to the internet, and data could leave the machine  | Network globals (`fetch`, `WebSocket`, `XMLHttpRequest`, `EventSource`, `WebTransport`, `RTCPeerConnection`, `sendBeacon`) and network modules are rejected while `hosts` in `policy/<id>.json` is empty. Each listed host must appear in the README. On Linux, the smoke test runs under `strace` and fails on any connection that is not to the loopback address |
| No telemetry, analytics or data collection                                     | The listing policy forbids it, and users do not expect it                                | Review. Each README says so                                                                                                                                                                                                                                                                                                                                        |

### Code

`scripts/check-policy.mjs` parses every `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs` and
`.cjs` file in a plugin, and every inline `<script>` in its HTML files, with the TypeScript
compiler (`ts.createSourceFile` and a walk over the syntax tree), not with text search. Code inside
type annotations is ignored, because it never runs. A file that does not parse fails.

| Rule                                                                                | Why                                                                                                   | What the parser rejects                                                                                                                                                                                                                                                                                                                                                                                             |
| ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Imports only from the plugin's own files, `orca`, and allowed Node builtins         | Plugins have no dependencies, and each builtin widens what the code can do                            | An import of a Node builtin not in `modules` in `policy/<id>.json`; `node:vm`, `node:worker_threads`, `node:module`, `node:inspector`, `node:repl`, `node:wasi`, `node:v8` and `node:cluster` always; a relative import that leaves the plugin folder; packages and URLs, including `data:` URLs                                                                                                                    |
| No code that review cannot see                                                      | Code built from strings at run time escapes review and every check                                    | `eval`, `Function` (so `new Function` and `Reflect.construct(Function, ...)`), any `.constructor` access, `WebAssembly`, `Worker`, `SharedWorker`, `importScripts`, `createRequire`, `process.getBuiltinModule`, `process.binding`, `process.dlopen`, `process.mainModule`, `setTimeout` or `setInterval` with a string, strings that start with `javascript:`, `vbscript:` or `data:`, creating a `script` element |
| Every import is visible                                                             | A computed module name hides what is loaded                                                           | `import()` and `require()` with anything but a string literal; `require` used as a value                                                                                                                                                                                                                                                                                                                            |
| No reaching globals by a computed name                                              | `globalThis['fe' + 'tch']` hides a network call from the rules above                                  | Any computed access on `globalThis`, `global`, `window`, `self` or `process`, and using `globalThis`, `global`, `window` or `process` other than as `name.property` or with `typeof`                                                                                                                                                                                                                                |
| No names assembled from pieces                                                      | `'inner' + 'HTML'` hides a forbidden name                                                             | Property names built from strings, and any string that the checker can fold (concatenation, templates, `join`, `String.fromCharCode`, `atob`, `const` values) into a forbidden name                                                                                                                                                                                                                                 |
| Child processes only through `execFile` or `spawn`, with a literal, allowed program | A shell or a computed program path can run anything                                                   | `exec`, `execSync` and `fork`; `execFile`, `execFileSync`, `spawn` and `spawnSync` unless called directly with a string-literal absolute path listed in `programs`; the `shell` option set to anything but `false`; shells, `env`, `curl`, `nc`, `osascript`, interpreters and similar programs even when listed; passing these functions around, for example to `promisify`                                        |
| Panels never put data into HTML                                                     | Process names and other sampled text are untrusted. Put into HTML, they could run script in the panel | `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `createContextualFragment`, `srcdoc`, `setHTMLUnsafe`, `parseHTMLUnsafe`, and in HTML files inline event handler attributes (`onclick=`), `srcdoc=`, `javascript:` and `vbscript:` URLs, and scripts from outside the plugin                                                                                                                      |

The only exception to the literal-program rule is a `dynamicPrograms` entry in the plugin's policy
file. It names one file, one exported function in it, and a reason. Inside that function, and only
there, `execFile` and `spawn` may take a program that is not a literal; the `shell` ban still
applies. It exists for programs with no fixed path, such as Orca's own CLI. **The maintainer reviews
every such exception, and the code of its function, before it merges.** See
[policy/README.md](../policy/README.md).

To keep the literal-program rule workable, give each command its own call site, and share the rest
of the work through a helper that takes a callback:

```ts
run((done) => execFile('/bin/ps', ['-A', '-o', 'pid='], OPTIONS, done))
```

### Files

| Rule                                                                                                                                                         | Why                                                                                      | How CI checks it                                                                                                                                                                           |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Every plugin has `README.md`, `CHANGELOG.md`, `LICENSE`, and `"license": "MIT"` and `"repository": "https://github.com/pblobp/orca-plugins"` in its manifest | Orca installs only the plugin folder, and the directory rejects a plugin with no license | Checked. `LICENSE` must be a byte-for-byte copy of the root `LICENSE`                                                                                                                      |
| Every plugin has `policy/<id>.json`                                                                                                                          | The checks need to know what the plugin may use                                          | Checked. Unknown keys and policy files for plugins that do not exist fail                                                                                                                  |
| No npm runtime dependencies by default. A vendored library is listed in the plugin's `THIRD_PARTY.md` with its source, version, hash and license             | Dependencies bring code nobody here reviewed, and updates to it                          | No `node_modules`, `package.json` or lockfile inside a plugin. `THIRD_PARTY.md`: review                                                                                                    |
| Readable source only. No minified or obfuscated files                                                                                                        | Review needs code a person can read; the listing policy forbids hiding code              | Lines in code, HTML, CSS and JSON files are at most 200 characters, and files named `*.min.*` fail                                                                                         |
| No binaries, archives, symlinks or TTF/OTF fonts                                                                                                             | The directory rejects them, and a binary cannot be reviewed                              | Every file must be UTF-8 text without NUL bytes, or a PNG, JPEG, WEBP, WOFF or WOFF2 file whose content matches its extension. Archive, executable and font extensions fail. Symlinks fail |
| Within Orca's limits                                                                                                                                         | Orca refuses larger plugins                                                              | At most 2,000 files and folders and 50 MiB per plugin, and 1 MiB per `.ts`, `.tsx`, `.mts` or `.jsx` file                                                                                  |
| Generated typings are not committed                                                                                                                          | `.orca/` is machine-specific and would change the content hash                           | Committed files under `.orca/` fail                                                                                                                                                        |

The file checks look at the files Git would commit: tracked files and new files that are not
ignored.

### Versions and the catalog

| Rule                                             | Why                                                                                                                                                                                           | How CI checks it                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A changed plugin gets a higher version           | Every byte under `plugins/<id>/` is part of what users install, its README and images included. The directory keeps the first content it sees for each `id@version` and refuses a changed one | `scripts/check-versions.mjs`. If the folder differs from its state at the newest `v*` tag merged into `HEAD`, its `version` must be higher than at that tag. A version may never be lower than one released at any earlier tag, and a version released at an earlier tag may not come back with other files. Before the first tag, every plugin is a first release |
| A version already in the catalog keeps its files | The catalog entry pins a commit and a content hash                                                                                                                                            | `scripts/check-versions.mjs` fails when a plugin's current version is listed in `orca-catalog.json` at a commit whose folder differs                                                                                                                                                                                                                               |
| A listed release is never edited                 | Users and the directory trust that a listed version never changes                                                                                                                             | `scripts/check-catalog.mjs --base <ref>`: no existing `id@version` entry in `orca-catalog.json` is changed or removed                                                                                                                                                                                                                                              |
| The catalog matches the repository               | `orca plugin validate` checks only the catalog's shape: it accepts made-up commits and hashes                                                                                                 | `scripts/check-catalog.mjs`: every id is `pblobp.<id>` with the source `plugins/<id>` of this repository; releases are newest first; every listed commit exists, is an ancestor of `HEAD` and holds that version. With `--with-orca`, each plugin's newest entry must equal what `orca plugin release-entry` prints for its commit                                 |

### Tests and fixtures

| Rule                                                                | Why                                                                          | How CI checks it                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------------------------------------------------- | ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Test fixtures hold no personal data                                 | Captured command output contains user names, host names, addresses and paths | `scripts/check-policy.mjs` scans every file under a `fixtures` folder in `tests/`. It rejects home paths other than `/Users/user`, `/home/user` and `/Users/Shared`; MAC addresses other than `00:00:5e:00:53:xx`; IP addresses outside loopback and the documentation ranges `192.0.2.x`, `198.51.100.x`, `203.0.113.x` and `2001:db8::`; host names ending in `.local`, `.lan`, `.home`, `.internal` or `.localdomain` other than `host.local`; email addresses; and, when run outside CI, the local user name and host name. Clean captured output before you commit it |
| Behaviour changes have tests; bug-fix tests fail first              | A test that never failed proves nothing                                      | Review                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Works on macOS, Linux and Windows, or degrades with a clear message | Users run all three                                                          | The smoke test, `tools/<id>/smoke.ts`, runs on all three in CI                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

### Style

| Rule                                                                                                                        | Why                                                            | How CI checks it                                           |
| --------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- | ---------------------------------------------------------- |
| TypeScript uses erasable syntax only: no enums, no parameter properties, `import type` for types, `.ts` on relative imports | The same file then runs in Orca, under `tsc` and in plain Node | `tsc` with `erasableSyntaxOnly` and `verbatimModuleSyntax` |
| Consistent formatting                                                                                                       | Smaller diffs, easier review                                   | `prettier --check`                                         |
| Styled from Orca's `--orca-*` theme variables; works in light and dark and at a 220 px sidebar                              | Plugins should look like part of Orca with any theme           | Review, from the screenshots in the pull request           |
| No comments in source                                                                                                       | Explanations belong in the README, a doc or the commit message | Review                                                     |
